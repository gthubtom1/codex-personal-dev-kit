# Current Status

## Milestone

The Codex Personal Dev Kit 0.2.7 makes the 21-dimension release review a machine-checked precondition for every formal version, adds the read-only `next_step.py` entry script so execution order comes from a script instead of prose, makes "research existing practice before writing from scratch" the default for new capabilities, and adds staging-time secret rescan, lockfile-drift and large-file protections. It is the first version that had to pass its own release-review gate.

## Working State

- Source candidate: `codex-personal-dev-kit` version `0.2.7` on the current local branch.
- Mother folder: the repository's portable workspace template is the canonical rule source. The live `D:\开发\AGENTS.md` still reflects the v0.2.6 render; reconciling it is the remaining next action. Workspace and project templates do not write any native subagent model, reasoning, concurrency, enablement, or interruption setting; Codex official defaults and user-owned configuration remain authoritative.
- The installed standalone runtime is rebuilt from the current source checkout, so the gate-aligned guide is what a task actually runs rather than what the repository merely contains. README and `docs/RESTORE.md` pin the restore clone to the current formal tag.
- Standalone installation can start from a nonexistent mother folder and writes the exact rendered canonical detailed rules. Existing differing rules/configuration are preserved, but the install plan labels the rules as custom and diagnosis fails the canonical-template check without printing their content. Repeated installation remains idempotent. It does not install a Plugin, lifecycle Hook, custom Agent, or Rules file.
- Installation records every fully managed Skill/runtime/template file and its SHA-256 hash in `managed-files.json`. Diagnosis detects missing or changed files; updates back up and remove only unchanged stale Dev Kit files while preserving user-modified stale files with a warning.
- Legacy Plugin, custom-agent, and Dev Kit Hook detection remains only as an explicit migration/diagnostic path; it is not a runtime dependency.
- Formal versions are recorded in `docs/VERSIONS.md`; the guard can mark the current verified checkpoint or safely backfill a verified ancestor during onboarding. Restoration creates a new checkpoint while preserving newer history, tags, and the complete index.
- Formal versions additionally require a completed 21-dimension release review in `docs/RELEASE-REVIEW.md` (requirements through AI completion audit) recorded for that exact version inside the tagged checkpoint, or inside the current checkpoint when backfilling history. Missing files, mismatched versions, missing dimensions, unknown statuses, and empty evidence are refused; honest `not-verified` entries with reasons pass. The static gate cannot prove evidence authenticity; the audit checklist spot-checks `verified` evidence reproducibility instead.
- The three Chinese bootstrap scripts (`diagnose.ps1`, `install.ps1`, `update.ps1`) now carry a UTF-8 BOM, so PowerShell 5.1 on a cp936 console (the beginner audience's default Chinese Windows) no longer garbles their output or the layout/sync gates that depend on them; a portability test turns red if any non-ASCII PowerShell script loses its BOM.
- A read-only `next_step.py` entry script reports the current guarded stage and prints the exact next commands (onboarding, contract start, stage, verify, complete, checkpoint, pending formal versions and their release review), so execution order comes from a script instead of prose. It flags unregistered user changes for ownership confirmation before recommending a contract.
- Once a contract has staged paths, `next_step.py` no longer derives its own stage from "are there any verification runs". It calls the gate's own `completion_blockers`, so the guide names the earliest reason `complete` will refuse — stale project facts, an un-updated `docs/STATUS.md`, unstaged or post-verification edits, or an active feature with no successful run — and suggests the command that clears exactly that reason. The suggested `--feature` set is the gate's required set, not just the declared changed IDs.
- Every `next_step.py` run, in every state, ends with the objective shapes that require researching existing practice before writing anything: a new capability/integration/algorithm or an unfamiliar API or standard, an unfamiliar error, being about to answer a key question from impression, having no approach or wavering between two, and being about to ask the user. Deciding whether to look something up is the judgment an agent is worst at — it skips the search exactly when it feels certain — so the list is observable shapes rather than a prompt to self-assess, and it is not gated on which branch of the guide ran. The same block names what searching cannot answer: the current state of this project (a function's real behavior, whether a test actually passed, what a file looks like now) only comes from running commands and reading source and git.
- The contract lifecycle is fully documented for a Skill-driven agent: `cancel` (abandon while the baseline is untouched) and `close` (drop an already checkpointed verified contract) have a feature-protection section, and the staging refusal for pre-existing user work now names `cancel` + `--own-path` as the way out instead of leaving a dead end. `feature_guard.py --help` describes every subcommand including `hook`, and the completed contract no longer stores the write-only `verifiedWorktreeFingerprint` field.
- A third-party two-reviewer round (diff defect review plus multi-dimension gap review) was merged back: git subprocess output now decodes as UTF-8 with replacement so Chinese review content cannot crash cp936 consoles; historical backfill only borrows the current checkpoint's review when the target tree has no review of its own and a conflicting target review refuses the tag; review tables refuse duplicated rows, multiple version lines, and rewritten dimension keys while honest non-verified statuses still pass.
- Guarded staging now refuses likely credentials (key blocks, provider tokens, signed JWTs, URL-embedded passwords), warns about oversized binaries and manifest changes whose existing lockfile is left unstaged, and PowerShell/batch/shell scripts count as source. Verification runs must bind at least one feature ID, and the publish remote-tag-conflict branch is covered by a red test.
- Raw Git tag creation, deletion, movement, and overwrite remain blocked; explicitly read-only tag listing and verification are allowed for audits.
- The short global AGENTS template substitutes the selected Codex Home, so a different Windows username does not retain `C:\Users\Administrator` in installed Skill guidance.
- `docs/RESTORE.md` defines the supported new-computer path: fixed Git checkout, preview/apply installation, full Desktop restart, diagnostics, and separate project backups.
- Formal-version creation verifies both `package.json.version` and a tracked root `VERSION` marker when present, preventing a Git tag from disagreeing with the distributed version.
- Explicitly authorized remote backup now uses `feature_guard.py publish`: it requires a clean verified checkpoint, an exact matching remote URL, the checked-out branch, immutable documented formal tags, dry-run and atomic exact-ref push, and post-push remote verification. Raw/force push, remote-ref deletion, Release creation and deployment remain blocked.
- Guarded `sync` fetches one exact authorized remote branch and only fast-forwards when history is linear; guarded `integrate` does the same for one exact local source branch. Divergence is preserved for a separately scoped conflict-resolution task.
- Guarded `unstage` operates only on current-contract paths and preserves their working content. Guarded `remove-worktree` refuses current/locked/dirty/ignored/untracked Worktrees and any target with commits not already in the current history.
- The safe-development Skill now bundles `install_global_tool.py`, which supports only explicitly confirmed winget package ID, exact version and scope, refuses implicit upgrades/downgrades, and verifies the installed version.
- Standalone tree copying excludes every `__pycache__` segment and `.pyc`/`.pyo` file. Managed-file reconciliation removes a previously installed unchanged cache artifact rather than carrying interpreter output into future computers.
- The project audit lists every file above a reported size threshold (50 MB by default, `--large-file-bytes` to change it) that no ignore rule covers, so the weight a clone or a whole-project scan actually carries is visible before it becomes a problem. It only reports: no file is deleted and no ignore rule is edited. Ignored paths stay out of the list, which is what separates real weight from storage the project already excludes.
- New parallel work copies are planned outside the opened project. The placement logic is its own `scripts/worktree_layout.py` module so the 111 KB `feature_guard.py` only gains its subcommand wiring. `feature_guard.py worktree-path --root . --name <label>` derives `.<project-name>-worktrees/<label>` beside the project from the current project at run time, with no machine-specific path anywhere, and refuses an occupied target instead of reusing it. The command-safety guard blocks a `git worktree add` whose path resolves inside the project and names that command as the way out. A copy hidden behind ignore rules cannot be read by the assistant that still has to work in it, so placement, not an ignore entry, is the fix. Existing work copies are never moved.

## Current Limitations

- Explicit safety scripts depend on the Skills following the workflow; there is intentionally no lifecycle Hook that can alter Codex native tool behavior.
- Local Git recovery protects work on this machine but is not an off-device backup.
- Explicit global Codex settings are outside Dev Kit ownership. The diagnostic now warns about known plaintext bearer/API/secret keys without printing values; the current host still requires user-led credential rotation/removal and review of any global main-model default.
- Secret detection covers common named files, provider tokens, assignment-style keys, and bounded large-text handling. It is not a dedicated release security scanner.
- Markdown anchor checking intentionally approximates common GitHub-style slugs; unusual renderer-specific extensions may still require manual review.
- The current Codex task began before any future standalone update. A new task is required after an approved install so Codex reloads the short global instructions and Skills. Exact cross-model availability remains task- and desktop-version-dependent and cannot be guaranteed by repository configuration.
- The public distribution uses MIT terms. Future direct copying or vendoring of third-party source would require a fresh license and attribution review beyond the current method-level acknowledgements.
- The v0.2.7 review shipped with its findings recorded rather than fixed. F-15-01 (P2), F-21-01, A-01 and A-02 are now closed; the remaining recorded finding and the nine `partial` dimensions still stand, because that evidence was read-only — a successful `rollback`, a successful `restore-version`, and the `-MigrateLegacy` path are argued from code and unit tests rather than reproduced end to end.
- `next_step.py` reports the earliest gate that refuses, not every problem at once. Clearing a project-facts blocker can reveal a staging or coverage blocker on the next run; this matches the gate's own order but means the guide is not a single complete to-do list.
- Complex divergent-history resolution, global-tool upgrade/downgrade, non-winget managers and production release/deployment remain outside these first guarded paths. They require separate invariants and tests; the assistant must not hand raw commands to the beginner as a workaround.
