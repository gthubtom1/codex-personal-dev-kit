# Prepare Codex Goal

先广泛分析，再狭窄执行。主动发现用户没有说出的必要问题，但不要把建议自动变成本次实施范围。

## 工作流

1. 尊重当前信息边界。用户不允许读取项目时，只基于其描述工作；允许读取时，优先看 `AGENTS.md`、`docs/PROJECT.md`、`docs/STATUS.md` 和相关代码入口。
2. 用普通语言复述目标、使用者和预期结果。区分“想完成的结果”和“想到的实现方式”。
3. 读取 [requirement-expansion.md](references/requirement-expansion.md)，从 20 个维度检查遗漏。把发现分为：本次必需、建议纳入、以后再做、明确不做。
4. 对重大技术选择给出 1 个推荐方案和必要的备选方案，说明成本、风险和可逆性。不要把“架构”当成脱离需求的先行大工程。
5. 读取 [risk-and-permissions.md](references/risk-and-permissions.md)，标出可自动执行、必须询问和禁止自动执行的动作。
6. 读取 [goal-contract.md](references/goal-contract.md)，形成包含结果、范围、非目标、约束、验收、验证、风险、权限、检查点和停止条件的 Goal 合同。
7. 按复杂度选择执行方式：小任务直接做；多步骤任务先计划；长任务使用持久 Goal；存在独立调查流时再调用 `$orchestrate-codex-team`。
8. Goal 文本控制在 4000 字符以内。细节较多时把执行计划放入项目文档，只在 Goal 中引用该文件和完成标准。
9. 用户说“做到可用/完成它/继续直到完成/无人值守/不要停”等结果导向要求，且任务确实包含多个步骤时，视为已授权持久 Goal；范围明确后立即设置。小型单步修改或仅分析请求不创建 Goal。设置后仍沿用当前 sandbox 和 approval 边界。

## 零基础沟通

- 推荐一个默认选择，不把所有技术选项丢给用户。
- 解释每个需要用户决定的问题会改变什么。
- 能从项目事实安全推断的内容直接推断；只有会明显改变结果或风险时才提问。
- 把新发现的扩展需求放入候选清单，不擅自实现。

## 输出

先给推荐结论，再给 Goal 合同。最后列出需要用户决定的事项、执行方式和第一批验证命令。
