# 功能回归与项目记忆

## 三层记忆

1. `docs/FEATURES.md`：用户可见能力、关键规则、状态和验证入口。
2. 自动化测试：可执行的行为记忆，证明功能仍然存在。
3. Git：每个稳定切片的可恢复历史。
4. 当前变更契约：本次允许改变什么、必须保护和复核什么；只保留当前任务并由 Hook 恢复。

聊天、memory 和 STATUS 只帮助恢复当前工作，不能替代这三层。

## 修改前

- 找到受影响功能 ID、入口、主要状态和已有测试。
- 沿完整接线链路检查 UI、设置保存、API、后台任务、持久化和错误处理，避免只改其中一段。
- 列出必须保持的旧行为和本次明确改变的行为。
- 对缺少测试的关键旧功能，先补最小特征测试或可重复人工检查。
- 检查多个任务是否正在修改同一代码或同一可变资源。
- 在第一次编辑前启动 bundled feature guard；把邻接能力加入显式验证列表。

## 修改后

- 验证新验收条件。
- 重新运行受影响功能及关键主流程。
- 让独立审查者比较功能清单、diff 和测试，查找被删除、未接线或状态遗漏的能力。
- 完成 feature guard 并记录精炼验证证据；契约未通过时不得创建完成检查点。
- 更新 FEATURES 的当前事实和验证入口，不记录开发流水账。

## FEATURES 限流

主文件保持索引式、可搜索。功能较多时按稳定业务领域拆到 `docs/features/<domain>.md`，主文件只保存领域链接和关键主流程。不要为每次小改动新增一份永久规格文档。
