# 从一句话到可靠软件

## 1. 理解结果

识别用户、问题、成功画面和最重要使用流程。主动检查必要的错误、数据、安全和运维条件，但只把影响当前可用性的内容纳入第一阶段。

## 2. 建立功能基线

已有项目先读取 `FEATURES.md`、关键测试和当前状态。缺少功能清单时，从用户说明、界面、路由、公开 API、后台处理和测试中提炼当前能力，标注不确定项。第一次编辑前建立临时当前变更契约，锁定受保护功能和回归范围。

## 3. 选择最小架构

先支持当前第一批真实能力，并留下合理扩展边界。避免大而全的平台，也避免继续把互不相关的职责堆进同一模块。架构选择必须能说明模块责任、接口、数据流和测试位置。

## 4. 制定纵向切片

每个切片从用户入口贯穿到可观察结果，包含必要测试和错误处理。优先交付一个完整小流程，不同时铺开大量半成品模块。

## 5. 实现与检查点

默认在当前开发线上工作；每个验证通过的稳定切片在结束前必须创建本地回退点。分支不是版本保存方式，隔离副本只在能减少真实冲突时使用，避免为了流程而制造合并工作。

## 6. 验证和独立审查

先运行最相关检查，再覆盖改变的功能、邻接功能和所有 active 旧功能。大型项目可以按真实测试入口分批覆盖，但不能只验证 critical 旧流程。完成 feature guard 后才可提交。复杂或高风险改动由独立只读代理比较 Goal、FEATURES、当前变更契约、diff 和测试证据。

## 7. 同步当前事实

更新功能、架构和状态中真正改变的部分。复杂任务的单个临时计划在完成后删除；已完成过程、调试日志和旧状态不追加到长期文档，由 Git 保存。

## 8. 继续或结束

同一结果还有明确切片时继续；出现新成果时结束当前任务并生成下一句提示。不要让一个任务无限承载整个项目生命周期。
