# 风险相称的质量门

## 低风险

文案、局部样式或内部重命名：

- 运行相关格式化或静态检查。
- 运行最接近改动的测试。
- 查看最终 diff 和界面文本是否溢出或破坏布局。

## 中风险

业务逻辑、多个模块、API 调用或状态管理：

- 添加或更新单元/集成测试。
- 运行类型、lint、相关测试和构建。
- 验证成功、失败、空值和重试路径。
- 检查兼容性、错误消息和日志是否泄露数据。

## 高风险

认证、支付、权限、并发、数据库、迁移、文件上传或发布配置：

- 先建立回归或特征测试。
- 使用独立审查者检查安全、数据完整性和回滚。
- 在隔离环境验证迁移、备份和失败恢复。
- 运行更广测试套件和端到端流程。
- 生产动作必须有独立授权和受控流程；不存在受控流程时停止并报告，不能把原始命令交给零基础用户。

## 失败处理

- 首次失败：读取真实错误并修复最可能原因。
- 连续失败：缩小复现，检查环境和假设，不盲目重复同一命令。
- 无法运行：说明缺少的工具、凭据或服务，并提供下一条最小验证路径。
- 不因测试昂贵就声称通过；明确区分已验证、部分验证和未验证。

## 证据绑定

在已有 Dev Kit 项目中，最终用于 feature guard 的自动化检查必须通过 `feature_guard.py verify -- <command>` 运行。门禁记录真实退出码和内容快照；聊天中的“测试通过”或任意 `--evidence` 字符串只能作为补充说明，不能解锁提交。

调用有副作用的工具之后要验状态，不要读它的回话。回话是它说的，状态是它做的。已经踩过的三种：清除截止时间的接口回“已重设”而截止没清；空契约下的 `close`／`cancel` 返回 exit 0 并打印“已封存”而实际没动；`git add .` 永远成功，因此永远不会告诉你它刚卷进了别人的在途改动。

## 修缺陷：先红后绿，两份输出都要交

只交绿的那一次不算——无法分辨它是真修好了，还是又写了一条恒绿的假守卫。顺序固定：

1. 先写守卫，在**未修的代码**上跑，确认它红，并且**红在该红的那几条上**（红的条数对不上，说明它测的不是这个缺陷）。
2. 再改代码，重跑，确认转绿。
3. 两次的原始输出都留下；只有第 2 步的输出等于没有证据。
4. 已修好的缺陷若要复核，把缺陷装回去让守卫重新变红，撤回后用 `git hash-object` 比对确认变异无残留。

## 写守卫的三件套

一条守卫缺了其中任何一件，都可能在缺陷仍然存在时显示绿色：

- **夹具自检**：造出来的东西必须真是要测的那个形状，取不到就当场报错，不要返回空串或跳过而悄悄变绿。曾经有一条守卫因为夹具是手捏的，被测的那条代码路径一次都没走到，却稳定报“通过”。
- **正控**：该拦的必须真被拦住。
- **负控**：不该拦的必须真的放行——否则一条“一律拒绝”也能骗过正控。

覆盖了输入却没覆盖“这条检查本身还在不在”，等于没有守卫。
