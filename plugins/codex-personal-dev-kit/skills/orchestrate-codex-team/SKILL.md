# Orchestrate Codex Team

主任务持有需求、范围和最终决策。这里的“子代理”只指 Codex 当前任务内部、由原生 collaboration 工具管理的 subagent。

## 原生边界

- 用户要求启动子代理时，直接使用 `spawn_agent`；需要等待、补充任务或停止时使用 `wait_agent`、`send_message`、`followup_task` 或 `interrupt_agent`。
- 不得使用 `create_thread`、`fork_thread`、`send_message_to_thread`、`handoff_thread` 或任何可见聊天/任务功能模拟子代理。
- 新 Codex 任务是用户可见的长期上下文，不是子代理。只有用户明确要求创建、分叉、交接或继续另一个任务时，才使用任务管理功能。
- 不要为了启动子代理而修改 Codex、安装另一套代理系统或创建永久通信文档。可用的角色配置只负责约束原生 subagent 的职责。
- Dev Kit 不得注册替代代理的 MCP/App 工具、安装生命周期 Hook 或关闭 `agents.enabled`/`features.multi_agent`。任务、Worktree、Git 审查面板和 Appshots 保持 Codex 原生语义。

## 子代理模型策略

- 主对话模型由用户在 Codex 中选择，本 Skill 不锁定主对话模型。
- 默认子代理使用 `gpt-5.6-luna`，每个子代理的推理强度必须为 `max`。
- 子代理不是固定 1 个；按任务拆分多个有界并行工作。有效并发上限取配置的 `max_concurrent_threads_per_session` 与当前原生可用槽位的较小值（模板默认 6，不含主线程）；请求总数超过有效上限时分波次完成，保持用户指定的总数量和模型比例，不得静默减少。
- 用户明确指定组合时，例如“2 个 Sol、3 个 Luna”，按指定数量分别调用 `gpt-5.6-sol` 和 `gpt-5.6-luna`，每个都使用 `max`。
- 第一次调用前检查当前模型目录和原生工具参数是否支持每个请求模型及 `max`。不可用时不得静默换模型或减少数量，应报告兼容问题。
- 未指定模型时依赖配置中的 Luna/max 默认值；显式指定 Sol/Luna 时，使用原生 `spawn_agent` 的单次调用参数，并同时传入 `fork_turns="none"` 或明确的正整数 fork 深度，因为模型/推理覆盖不能与默认的完整历史 fork 混用。除非用户明确要求持久命名代理，不创建自定义 Agent 文件。
- 参数序列化失败表示子代理没有启动。不得反复重试错误参数，也不得把失败调用写成已完成的独立检查。

显式指定模型时的调用约束示例：

```text
spawn_agent(..., model="gpt-5.6-sol", reasoning_effort="max", fork_turns="none")
spawn_agent(..., model="gpt-5.6-luna", reasoning_effort="max", fork_turns="none")
```

这只是原生调用参数约束，不是要创建自定义 Agent 文件。

## 选择执行形态

读取 [agent-routing.md](references/agent-routing.md)，然后选择最小足够方案：

- 单代理：一个模块、一个清晰结果、低风险改动。
- 原生子代理：当前结果内部有一个或多个有界的探索、资料、测试或审查流，或用户明确要求启动子代理。
- Worktree：两个写入任务确实需要并行，或计划任务必须与本地未完成工作隔离。

不要为了显得专业而固定启动很多代理。子代理会增加 token、等待和协调成本。

## 编排规则

1. 先定义主任务的 Goal、共享事实和不允许改变的边界。
2. 使用原生 `spawn_agent` 启动子代理；普通复杂任务通常启动 2 到 3 个，用户明确指定的数量优先，超出有效并发上限就分波次。每个子代理只交付一个明确结果，不得继续派生子代理，除非任务明确授权。
3. 优先并行只读工作：代码定位、架构分析、官方文档核对、安全审查、测试缺口和日志分析。
4. 同一 checkout 默认只有主代理写入。探索者、架构师和审查者保持只读。
5. 并行写入必须使用不同 Worktree、不同分支和明确文件所有权；不得让两个任务同时修改同一文件或共享可变数据。
6. 给子代理最少且充分的上下文，不发送预期答案或主代理结论。要求引用文件、命令或其他证据。
7. 独立工作可并行启动；有依赖的工作按阶段进行。通过原生等待接口收集当前阶段结果后再作整合决定。
8. 使用 [result-contract.md](references/result-contract.md) 约束返回内容，要求精炼结论，不倾倒原始日志。
9. 主代理检查冲突、证据和遗漏后再决定是否实施。子代理建议不自动扩大范围。
10. 汇总完结果后结束当前内部代理协作，记录真正影响项目的结论到代码、测试或精炼文档；不要创建、归档或转发用户可见任务来清理子代理。

## 推荐职责

- Explorer：只读定位代码、数据流和影响面。
- Architect：只读比较边界、接口和迁移方案。
- Reviewer：只读查找正确性、安全和测试风险。
- Verifier：运行验证并报告证据，不修改产品源码。

这些是任务职责，不要求安装或创建自定义 Agent。使用原生普通子代理，在调用参数中明确模型与 `max`，并在提示中写明职责和只读边界。

## 输出

报告所选执行形态、代理分工、写入所有权、阶段依赖、结果摘要和主代理最终决定。
