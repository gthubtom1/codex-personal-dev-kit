# 现有项目评估

## 先看什么

1. 用 `git status -sb`、`git log -5 --oneline` 和 `git worktree list` 了解版本状态。
2. 用 `rg --files` 获取目录轮廓，排除 `.git`、依赖、构建产物和缓存。
3. 查看语言或框架清单、锁文件、入口、测试配置、CI 和部署配置。
4. 对复杂度热点先看符号、主要区段、依赖和变更历史，不要为了“全面”把整份大型源码直接塞进上下文。
5. 运行已有说明中的最小启动或测试命令；说明与事实冲突时以实际结果为准。
6. 从界面、路由、设置、API、后台任务、持久化和测试提炼当前用户能力；只记录有证据的功能，并标出不确定项。

## 风险信号

- 一个文件同时承担 UI、状态、网络、数据和业务规则，且修改经常互相影响。
- 文件难以局部理解、无法独立测试、多人频繁冲突，或一次小改动需要触碰大量无关区域。
- 行数、圈复杂度和依赖数量可以作为线索，但不能单独决定是否拆分；项目类型和现有约定可能使大型文件合理。
- 没有锁文件、测试入口或可复现启动命令。
- `.env`、密钥、数据库文件或用户数据被 Git 跟踪。
- 长期存在大量未提交修改，或多个任务共享同一 checkout 写入。
- 文档只追加历史，当前状态无法快速定位。
- 功能清单只有名称，没有稳定 ID、完整接线链路或可重复验证，导致改动无法可靠判断旧能力是否仍存在。

## 确实需要拆分时

1. 先证明拆分能解决真实维护、正确性或协作问题。
2. 建立当前行为基线和最重要用户流程测试。
3. 画出入口、状态、I/O、数据模型和副作用边界。
4. 优先抽离纯函数、常量、类型、适配器和可独立测试的服务。
5. 每次只移动一个责任，保持外部接口和行为不变。
6. 每个切片运行验证并创建本地检查点。
7. 最后再处理命名、目录和公共接口清理。

## 接入时不要做

- 不在不了解行为时升级框架或全部依赖。
- 不把格式化整个仓库混入接入提交。
- 不删除用户看似无用但尚未确认的文件。
- 不创建远程仓库、push 或发布。
